# LobeChat — arckep fork operational notes

Дополнение к `CLAUDE.md` (upstream LobeHub guide). Здесь только то, что специфично для нашего форка `chat.arckep.ru`. **Не сливать с upstream `CLAUDE.md`** — этот файл живёт отдельно, чтобы не ловить конфликты при merge.

## Деплой prod (chat.arckep.ru)

|                   |                                             |
| ----------------- | ------------------------------------------- |
| URL               | <https://chat.arckep.ru>                    |
| Source            | `/opt/lobechat-src/`                        |
| Prod (standalone) | `/opt/lobechat/`                            |
| Service           | `image-studio-lobechat.service` (порт 3402) |
| Логи              | `/var/log/image-studio-lobechat.log`        |

### Билд + деплой

```bash
cd /opt/lobechat-src
bun run build # vite SPA + next Turbopack, ~6–9 min

# Оба rsync критичны. Забыть любой = 404 на чанках или SSR с stale-ссылками
rsync -a --delete /opt/lobechat-src/.next/ /opt/lobechat/.next/
rsync -a --delete /opt/lobechat-src/public/_spa/ /opt/lobechat/public/_spa/

systemctl restart image-studio-lobechat
```

**Почему именно так:**

- `.next/` целиком — не только `standalone/`. Next.js standalone в новых версиях кладёт SSR-шаблоны в `.next/server/app/spa/...body`, которые runtime-генерируют HTML со ссылками на JS-чанки. Старые `*.body` → браузер получает 404 на `_spa/assets/index-XXX.js`.
- `public/_spa/` — Vite SPA assets (`assets/index-*.js`, `index.html`). Старые чанки здесь → браузер грузит stale bundle без фиксов.
- `.env` в `/opt/lobechat/` не трогаем (он не входит в `.next/` и `public/_spa/`).

**Проверка после деплоя:**

```bash
cat /opt/lobechat/.next/BUILD_ID # должен совпадать с src
curl -sS -o /dev/null -w "%{http_code}" https://chat.arckep.ru/_spa/assets/$(ls /opt/lobechat/public/_spa/assets/index-*.js | head -1 | xargs basename)
# должен быть 200, не 404
```

## Arckep-специфичные модификации (за пределами upstream)

- **Auth**: бесшовная через cookie `.arckep.ru` + bridge с Image Studio. См. `arckep_token` в коде.
- **Биллинг**: в рублях, через FastAPI endpoint Image Studio backend
- **Брендинг**: LobeHub полностью заменён на Image Studio
- **Язык**: русский по умолчанию (cookie `LOBE_LOCALE`)
- **Stats**: ₽ вместо $
- **Models**: chat через Inworld Router (15 моделей + 4 Gemini image)
- **Безопасность**: hard-disable browser `fetchOnClient` для billed providers (revenue leak protection)

## Решения

- Вопрос: самоход агента сайтов (Wave 4) — серверный CAO или клиентский follow-up?
- Взяли: клиентский хук после `sendMessage` → `internal_execAgentRuntime` (скрытое продолжение, не дубль user bubble). Судья — `gemini-2.5-flash-lite` через `fetchPresetTaskResult` (тот же billing proxy). Потолок 150 ₽ из `GET /chat/api/arckep/topic-spend`. Макс. 2 ремонта, потом AskUserQuestion.
- Отвергли: их CAO / Upstash / `agent_operations` / verify_* таблицы; новый write-path биллинга; RuntimeExecutors (Gemini 6-layer).
- Почему: флаг `SITES_AUTO_CONTINUE_ENABLED = false` + `chatConfig.enableSitesAutoContinue` на дефолтном помощнике выключен. Живое не трогаем, пока не перевернём константу.

## Известные особенности

- **Kling video** доступен через Qwen-провайдер (см. `packages/model-runtime/src/providers/qwen/createVideo.ts`). Отдельный custom runtime не нужен.
- **Codegraph**: slug = `lobechat` (не `lobechat-src`). Проект индексируется web+AST без Joern (см. `/opt/lobechat-src/.agents/codegraph.json`).
- **Сжатие длинного чата:** после первого сжатия порог поднимается до 65% окна (гистерезис, идеи upstream #18626). Иначе сжатый контекст сидит около 50% и каждый мелкий tool-result снова гоняет суммаризацию — жжёт токены и может зациклить. `/compact` и автосжатие не стартуют, пока уже идёт сжатие этого же топика. RuntimeExecutors.ts не трогаем: решение «сжимать или нет» в GeneralChatAgent.

## Решения

- Вопрос: после сжатия снова сжимать сразу, если всё ещё >50% окна?
- Взяли: гистерезис 50% → 65% (и явный `recompressionThresholdRatio`, если задан).
- Отвергли: вечный skip (длинный чат упрётся в лимит) и тот же порог 50% (петля суммаризаций).
- Почему: свежее сжатие почти всегда около нижнего порога; одна tool-выдача не должна запускать второй проход.

## Задачи по расписанию (19.10.2026)

Цикл «пора ли запускать» живёт в студии (`image-studio`, раз в минуту); движок хранит задачи (`agent_cron_jobs`) и выполняет запуск.

- REST (служебный вход студии, как у остальных `arckep`-маршрутов): `/api/v1/arckep/cron-jobs` — `GET`, `POST`, `PATCH /:id`, `DELETE /:id`, `POST /:id/run {runId}`, `GET /:id/topics`. Код: `packages/openapi/src/controllers/arckep-cron.controller.ts`, `routes/arckep.route.ts`.
- Расписание (`src/server/services/arckepCron/schedule.ts`) проверяют и REST, и инструмент `lobe-cron`: только 5 полей, макросы `@hourly/@daily/@weekly/@monthly/@yearly`, не чаще раза в 30 минут (поле минут: одно число, два числа ровно через 30 или `*/30`), пояс по умолчанию `Europe/Moscow`.
- Запуск (`run.ts`): `execAgent({ trigger: 'cron', cronJobId, autoStart, headless })`, затем `updateExecutionStats` (только если операция стартовала; `remainingExecutions` не ниже 0, при 0 задача выключается). Повтор того же `runId` в течение 15 минут задачу второй раз не запускает.
- Окончание (`finished.ts`): локальный хук `onComplete` шлёт `POST ${IMAGE_STUDIO_API_URL}/api/internal/chat-tasks/finished` с `X-Arckep-Token`. Работает только при локальной очереди (`AGENT_RUNTIME_MODE` не `queue`); студия сама закрывает запуски старше часа.
- `ARCKEP_CHAT_CRON=1` — `lobe-cron` доступен в обычном чате (по требованию). Внутри запуска `trigger='cron'` он скрыт всегда; в системный контекст запуска (`evalContext.envPrompt`) добавляется пояснение «человека в чате нет» (`prompt.ts`).
- Ловушка: `AgentCronJobModel.update` при смене `cronPattern`/`timezone` обнуляет `lastExecutedAt` («чтобы сработало сразу»). Студия не должна считать это пропущенным запуском за последний час.

## Вложения для модели со зрением (19.10.2026)

- **Картинки** (`src/server/services/aiAgent/imageSlicing.ts`, `ingestAttachment.ts`): ширина ≤1536 без увеличения; цельная картинка остаётся одной, пока после сжатия не выше 3072 (экраны телефонов, фото); выше — вертикальные куски по 2048 с перекрытием 64 сверху вниз, до 12; не хватило — ширина до 768, потом куски выше 2048. Куски — отдельные файлы `имя.part-NN-of-MM.png|jpg`, у каждого подпись «часть i из N, разрезано сверху вниз». Вес куска ~1 МБ: текст — PNG, фото-куски — JPEG 4:4:4 (запрос Gemini inline ≤20 МБ). Раньше любая картинка сжималась до 1920 по длинной стороне: макет 2512×23050 доходил как 209×1920.
- **PDF** (`pdfPages.ts`): для моделей со зрением к текстовому слою добавляются страницы картинками — до 10 страниц, не больше 16 картинок на файл, высокие страницы режутся так же, у каждой страницы хотя бы одна. Рисует poppler (`pdftoppm`/`pdfinfo` с хоста, отдельным процессом: тайм-аут, низкий приоритет; пути — `PDFTOPPM_BIN`/`PDFINFO_BIN`). Выключатель: `ARCKEP_PDF_PAGE_IMAGES=0`; память одной программы poppler — `ARCKEP_PDF_MEMORY_MB` (по умолчанию 2048, через `prlimit`, 0 — без предела). Потолок сжатой копии — 30000 px по высоте: вытянутее (около 40:1) картинка не режется, а сжимается до 1920, страница PDF такой пропорции не рисуется. Зрение — тот же признак, что при вызове модели (`abilities.vision` в model-bank, неизвестная модель — со зрением).
- **Список вложений для модели** (`<attachments>`): в `messages.metadata.attachments` user-сообщения `execAgent` пишет по строке на файл — имя, тип, размер картинки в точках, адрес ОРИГИНАЛА `${APP_URL}/f/<id>/` (на проде `https://arckep.ru/chat/f/<id>/`; nginx отдаёт `/chat/f/` движку, тот отвечает 302 в хранилище). `MessageContent` рисует блок внутри `<files_info>` (`packages/prompts/src/prompts/files/attachments.ts`); он же живёт в истории между ходами и в текст человека не попадает. Когда список есть, подписанные адреса копий в `<image>`/`<file>` не повторяются (−1300 токенов на разрезанный макет). Оригинал картинки: файл из `input_file` — сам файл; картинка по адресу — запись файла человека по ключу (`FileModel.findByKey`, чужие файлы не находятся); внешняя картинка без записи, если её пришлось сжать или резать, — сохранённые куски с пометкой «копия, оригинал не сохранён». Размеры картинок из `file_id` не известны (их не читаем) — в строке без размера.
- **Вшитые картинки PDF** (`pdfImages.ts`, `pdfimages` из poppler): фото героя, врачей, услуг для HTML. Картинка с мягкой маской (SMask) → PNG с альфой; без маски — исходный JPEG без перекодирования; мельче 48 точек (линии, градиентные полосы) и дубли (тот же объект на нескольких страницах, тот же хеш) отброшены; до 30 на файл, просматриваются первые 40 страниц. Сохраняются файлами человека `<pdf>.image-NN.pP.png|jpg`, к сообщению НЕ прикрепляются (модель их не «смотрит» — только адреса в списке: «картинка N из <pdf>, стр. P, W×H»). Работает и для моделей без зрения. Выключатель: `ARCKEP_PDF_EMBEDDED_IMAGES=0`; путь к программе — `PDFIMAGES_BIN`; пределы памяти те же (`popplerRunner.ts`). Пределы против «бомб» (PDF приходит от кого угодно): распаковка по одной странице и только тех, где есть нужные картинки; по `pdfimages -list` оценивается сырой размер всех картинок страницы (тяжелее 512 МБ — страница пропускается, на файл — 1 ГБ), один файл ≤128 МБ (`prlimit --fsize`), папка ≤512 МБ, весь разбор ≤300 с; картинка больше 36 Мпикс не берётся. Шрифты PDF не трогаем (у макетов из Figma это Type 3 глифы).
- **Фоновая подготовка PDF** (`pdfPrepare.ts`): на тяжёлом PDF (макет письма 603×5532 пт) страницы рисовались 11–19 с, и модель начинала отвечать только после них. Теперь подготовка (вшитые картинки, затем страницы) стартует при загрузке файла — `POST /files` (`packages/openapi/src/services/file.service.ts`, не для документов базы знаний), пока человек пишет сообщение. Результат лежит в записи файла: `files.metadata.pdfPrep` (jsonb `||`, остальные ключи целы): ключи файлов-страниц, вшитые картинки, число страниц; повторно файл не рисуется. `execAgent` ждёт готовности не дольше `ARCKEP_PDF_PREPARE_WAIT_MS` (5000 мс); не успело — модель получает текст, а на строке PDF в `<attachments>` стоит пометка «страницы ещё рисуются…», ошибки нет; вшитые картинки (они готовятся первыми) идут в список сразу. На следующем ходе страницы подхватываются из записи в историю (в память, без записи в базу: `enrichHistoryWithPdf`), пометка снимается. Одновременно — не больше `ARCKEP_PDF_PREPARE_PARALLEL` (2) задач. Выключатели: `ARCKEP_PDF_PREPARE_ON_UPLOAD=0` (не готовить при загрузке; `execAgent` всё равно запустит и подождёт 5 с), `ARCKEP_PDF_PAGE_IMAGES=0`, `ARCKEP_PDF_EMBEDDED_IMAGES=0`. Запись в `files.metadata` недоверенная (tRPC `file.createFile` принимает любой `metadata` от клиента): всё, что читается из базы, проходит `verify` в `pdfPrepare.ts` — строгий формат, каждый `fileId` обязан быть файлом этого человека (`FileModel.findByIds` с его `userId`), ключ страницы берётся из записи ЕГО файла, а не из записи подготовки; подделка считается отсутствием записи (файл готовится заново), лишние поля отбрасываются. Живые задачи и ожидание — в памяти процесса: движок один процесс (`node server.js`); при нескольких процессах запись `processing` другого процесса считалась бы мёртвой. Страницы рисуются и для моделей без зрения (при загрузке модель неизвестна) — им они не отдаются. Пределы poppler подняты (страница 180 с, весь файл 420 с): под `nice 10` на занятом хосте (load 10–14 на 4 ядра) рисование растягивалось в разы, и прежние 60 с давали «нарисовано ничего»; модель результат не ждёт.
- **Системный промпт** (`ARCKEP_DEFAULT_SYSTEM_ROLE`, +130 токенов): готовую HTML-страницу, письмо, лендинг, SVG отдавать в `<lobeArtifact>`, не блоком кода; картинки в HTML брать из `<attachments>` и результатов `create_image`/`get_image` (заглушка — только если подходящей нет); шрифты — Google Fonts по ссылке, другой шрифт скачать в песочнице, сохранить файлом чата и подключить через `@font-face` по ссылке `/chat/f/…`. Раздел HTML навыка Artifacts (`packages/builtin-skills/src/artifacts/content.ts`) согласован с этим: запрет «никаких внешних картинок» заменён разрешением адресов вложений и результатов, `/api/placeholder` остаётся запасным. Раздел React навыка не менялся (там внешних картинок по-прежнему нет).
- **В истории студии** эти файлы видны как вложения сообщения (имена с `.part-NN-of-MM.` и `.page-NN.`): экран может их сворачивать по такому имени. Порядок вложений в базе теперь стабильный (`createdAt`, имя).

## Решения

- Вопрос: чем рисовать страницы PDF — pdfjs-dist (уже в зависимостях) или poppler?
- Взяли: poppler отдельным процессом. Отвергли: pdfjs + @napi-rs/canvas в процессе движка.
- Почему: изоляция разбора чужих PDF (зависание и падение не трогают сервис, есть тайм-аут), нет холста и памяти высоких страниц в процессе движка, зрелый рендер шрифтов; движок работает на хосте, poppler там стоит. Нет poppler — остаётся текстовый слой.
- Вопрос: с какой высоты резать картинку на куски?
- Взяли: выше 3072 после сжатия по ширине (а не «около 2048»), куски по 2048.
- Почему: экран телефона 1290×2796 и страница A4 при ширине 1536 (2172) должны остаться одной картинкой, а резка нужна длинным макетам.

- Вопрос: где хранить список вложений для модели — в тексте сообщения человека или рядом?
- Взяли: `messages.metadata.attachments`, рендер в контексте модели. Отвергли: дописывать список в `content` сообщения.
- Почему: человек в студии не должен видеть служебный список; из метаданных он читается из базы на каждом шаге и в истории, текст остаётся как написал человек.
- Вопрос: рисовать страницы PDF прямо в `execAgent` или заранее?
- Взяли: заранее, в фоне при загрузке файла; `execAgent` ждёт ≤5 с и без страниц не падает. Отвергли: рисовать синхронно (11–19 с до начала ответа на тяжёлом PDF) и отдельную очередь/таблицу (хватило `files.metadata`).
- Почему: студия грузит файл раньше, чем человек отправит сообщение; движок — один долгоживущий процесс, фон безопасен. Цена: страницы рисуются и тем, кто потом выберет модель без зрения.
- Вопрос: ссылки `/chat/f/<id>/` в списке вложений — публичные, не рискованно ли?
- Взяли: как есть (так просил владелец: адрес вставляется в HTML-предпросмотр и письмо). Отвергли: подписанные ссылки с сроком.
- Почему: `/f/:id` — штатный прокси файлов LobeChat без входа (запись ищется без userId, ответ — 302 на подписанный адрес на 5 минут); id — 12 знаков из 62 (около 71 бита), генератор `nanoid/non-secure` (не криптостойкий): перебором не угадывается, но и не секрет; адрес в письме должен жить дольше любого срока. Риск: у кого есть ссылка, тот видит файл, а модель может вставить её в публичную страницу; секретные вложения человек обрабатывает на свой риск.
- Вопрос: вшитые картинки PDF прикреплять к сообщению или только давать адреса?
- Взяли: только адреса в списке (файлы человека без привязки к сообщению). Отвергли: прикреплять как картинки.
- Почему: модель вставляет их в HTML по адресу, а «смотреть» их ей незачем — страницы уже даны целиком; иначе +13 картинок в запрос и в историю студии.
