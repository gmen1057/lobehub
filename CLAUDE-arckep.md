# LobeChat — arckep fork operational notes

Дополнение к `CLAUDE.md` (upstream LobeHub guide). Здесь только то, что специфично для нашего форка `chat.arckep.ru`. **Не сливать с upstream `CLAUDE.md`** — этот файл живёт отдельно, чтобы не ловить конфликты при merge.

## Деплой prod (chat.arckep.ru)

|                   |                                             |
| ----------------- | ------------------------------------------- |
| URL               | <https://chat.arckep.ru>                    |
| Source            | `/opt/lobechat-src/`                        |
| Prod (standalone) | `/opt/lobechat/`                            |
| Service           | `image-studio-lobechat.service` (порт 3402) |
| Логи              | `/var/log/image-studio-lobechat.log`        |

### Билд + деплой

```bash
cd /opt/lobechat-src
bun run build # vite SPA + next Turbopack, ~6–9 min

# Оба rsync критичны. Забыть любой = 404 на чанках или SSR с stale-ссылками
rsync -a --delete /opt/lobechat-src/.next/ /opt/lobechat/.next/
rsync -a --delete /opt/lobechat-src/public/_spa/ /opt/lobechat/public/_spa/

systemctl restart image-studio-lobechat
```

**Почему именно так:**

- `.next/` целиком — не только `standalone/`. Next.js standalone в новых версиях кладёт SSR-шаблоны в `.next/server/app/spa/...body`, которые runtime-генерируют HTML со ссылками на JS-чанки. Старые `*.body` → браузер получает 404 на `_spa/assets/index-XXX.js`.
- `public/_spa/` — Vite SPA assets (`assets/index-*.js`, `index.html`). Старые чанки здесь → браузер грузит stale bundle без фиксов.
- `.env` в `/opt/lobechat/` не трогаем (он не входит в `.next/` и `public/_spa/`).

**Проверка после деплоя:**

```bash
cat /opt/lobechat/.next/BUILD_ID # должен совпадать с src
curl -sS -o /dev/null -w "%{http_code}" https://chat.arckep.ru/_spa/assets/$(ls /opt/lobechat/public/_spa/assets/index-*.js | head -1 | xargs basename)
# должен быть 200, не 404
```

## Arckep-специфичные модификации (за пределами upstream)

- **Auth**: бесшовная через cookie `.arckep.ru` + bridge с Image Studio. См. `arckep_token` в коде.
- **Биллинг**: в рублях, через FastAPI endpoint Image Studio backend
- **Брендинг**: LobeHub полностью заменён на Image Studio
- **Язык**: русский по умолчанию (cookie `LOBE_LOCALE`)
- **Stats**: ₽ вместо $
- **Models**: chat через Inworld Router (15 моделей + 4 Gemini image)
- **Безопасность**: hard-disable browser `fetchOnClient` для billed providers (revenue leak protection)

## Решения

- Вопрос: самоход агента сайтов (Wave 4) — серверный CAO или клиентский follow-up?
- Взяли: клиентский хук после `sendMessage` → `internal_execAgentRuntime` (скрытое продолжение, не дубль user bubble). Судья — `gemini-2.5-flash-lite` через `fetchPresetTaskResult` (тот же billing proxy). Потолок 150 ₽ из `GET /chat/api/arckep/topic-spend`. Макс. 2 ремонта, потом AskUserQuestion.
- Отвергли: их CAO / Upstash / `agent_operations` / verify_* таблицы; новый write-path биллинга; RuntimeExecutors (Gemini 6-layer).
- Почему: флаг `SITES_AUTO_CONTINUE_ENABLED = false` + `chatConfig.enableSitesAutoContinue` на дефолтном помощнике выключен. Живое не трогаем, пока не перевернём константу.

## Известные особенности

- **Kling video** доступен через Qwen-провайдер (см. `packages/model-runtime/src/providers/qwen/createVideo.ts`). Отдельный custom runtime не нужен.
- **Codegraph**: slug = `lobechat` (не `lobechat-src`). Проект индексируется web+AST без Joern (см. `/opt/lobechat-src/.agents/codegraph.json`).
- **Сжатие длинного чата:** после первого сжатия порог поднимается до 65% окна (гистерезис, идеи upstream #18626). Иначе сжатый контекст сидит около 50% и каждый мелкий tool-result снова гоняет суммаризацию — жжёт токены и может зациклить. `/compact` и автосжатие не стартуют, пока уже идёт сжатие этого же топика. RuntimeExecutors.ts не трогаем: решение «сжимать или нет» в GeneralChatAgent.

## Решения

- Вопрос: после сжатия снова сжимать сразу, если всё ещё >50% окна?
- Взяли: гистерезис 50% → 65% (и явный `recompressionThresholdRatio`, если задан).
- Отвергли: вечный skip (длинный чат упрётся в лимит) и тот же порог 50% (петля суммаризаций).
- Почему: свежее сжатие почти всегда около нижнего порога; одна tool-выдача не должна запускать второй проход.

## Задачи по расписанию (19.10.2026)

Цикл «пора ли запускать» живёт в студии (`image-studio`, раз в минуту); движок хранит задачи (`agent_cron_jobs`) и выполняет запуск.

- REST (служебный вход студии, как у остальных `arckep`-маршрутов): `/api/v1/arckep/cron-jobs` — `GET`, `POST`, `PATCH /:id`, `DELETE /:id`, `POST /:id/run {runId}`, `GET /:id/topics`. Код: `packages/openapi/src/controllers/arckep-cron.controller.ts`, `routes/arckep.route.ts`.
- Расписание (`src/server/services/arckepCron/schedule.ts`) проверяют и REST, и инструмент `lobe-cron`: только 5 полей, макросы `@hourly/@daily/@weekly/@monthly/@yearly`, не чаще раза в 30 минут (поле минут: одно число, два числа ровно через 30 или `*/30`), пояс по умолчанию `Europe/Moscow`.
- Запуск (`run.ts`): `execAgent({ trigger: 'cron', cronJobId, autoStart, headless })`, затем `updateExecutionStats` (только если операция стартовала; `remainingExecutions` не ниже 0, при 0 задача выключается). Повтор того же `runId` в течение 15 минут задачу второй раз не запускает.
- Окончание (`finished.ts`): локальный хук `onComplete` шлёт `POST ${IMAGE_STUDIO_API_URL}/api/internal/chat-tasks/finished` с `X-Arckep-Token`. Работает только при локальной очереди (`AGENT_RUNTIME_MODE` не `queue`); студия сама закрывает запуски старше часа.
- `ARCKEP_CHAT_CRON=1` — `lobe-cron` доступен в обычном чате (по требованию). Внутри запуска `trigger='cron'` он скрыт всегда; в системный контекст запуска (`evalContext.envPrompt`) добавляется пояснение «человека в чате нет» (`prompt.ts`).
- Ловушка: `AgentCronJobModel.update` при смене `cronPattern`/`timezone` обнуляет `lastExecutedAt` («чтобы сработало сразу»). Студия не должна считать это пропущенным запуском за последний час.

## Вложения для модели со зрением (19.10.2026)

- **Картинки** (`src/server/services/aiAgent/imageSlicing.ts`, `ingestAttachment.ts`): ширина ≤1536 без увеличения; цельная картинка остаётся одной, пока после сжатия не выше 3072 (экраны телефонов, фото); выше — вертикальные куски по 2048 с перекрытием 64 сверху вниз, до 12; не хватило — ширина до 768, потом куски выше 2048. Куски — отдельные файлы `имя.part-NN-of-MM.png|jpg`, у каждого подпись «часть i из N, разрезано сверху вниз». Вес куска ~1 МБ: текст — PNG, фото-куски — JPEG 4:4:4 (запрос Gemini inline ≤20 МБ). Раньше любая картинка сжималась до 1920 по длинной стороне: макет 2512×23050 доходил как 209×1920.
- **PDF** (`pdfPages.ts`): для моделей со зрением к текстовому слою добавляются страницы картинками — до 10 страниц, не больше 16 картинок на файл, высокие страницы режутся так же, у каждой страницы хотя бы одна. Рисует poppler (`pdftoppm`/`pdfinfo` с хоста, отдельным процессом: тайм-аут, низкий приоритет; пути — `PDFTOPPM_BIN`/`PDFINFO_BIN`). Выключатель: `ARCKEP_PDF_PAGE_IMAGES=0`; память одной программы poppler — `ARCKEP_PDF_MEMORY_MB` (по умолчанию 2048, через `prlimit`, 0 — без предела). Потолок сжатой копии — 30000 px по высоте: вытянутее (около 40:1) картинка не режется, а сжимается до 1920, страница PDF такой пропорции не рисуется. Зрение — тот же признак, что при вызове модели (`abilities.vision` в model-bank, неизвестная модель — со зрением).
- **Список вложений для модели** (`<attachments>`): в `messages.metadata.attachments` user-сообщения `execAgent` пишет по строке на файл — имя, тип, размер картинки в точках, адрес ОРИГИНАЛА `${APP_URL}/f/<id>/` (на проде `https://arckep.ru/chat/f/<id>/`; nginx отдаёт `/chat/f/` движку, тот отвечает 302 в хранилище). `MessageContent` рисует блок внутри `<files_info>` (`packages/prompts/src/prompts/files/attachments.ts`); он же живёт в истории между ходами и в текст человека не попадает. Когда список есть, подписанные адреса копий в `<image>`/`<file>` не повторяются (−1300 токенов на разрезанный макет). Оригинал картинки: файл из `input_file` — сам файл; картинка по адресу — запись файла человека по ключу (`FileModel.findByKey`, чужие файлы не находятся); внешняя картинка без записи, если её пришлось сжать или резать, — сохранённые куски с пометкой «копия, оригинал не сохранён». Размеры картинок из `file_id` не известны (их не читаем) — в строке без размера.
- **Вшитые картинки PDF** (`pdfImages.ts`, `pdfimages` из poppler): фото героя, врачей, услуг для HTML. Картинка с мягкой маской (SMask) → PNG с альфой; без маски — исходный JPEG без перекодирования; мельче 48 точек (линии, градиентные полосы) и дубли (тот же объект на нескольких страницах, тот же хеш) отброшены; до 30 на файл, просматриваются первые 40 страниц. Сохраняются файлами человека `<pdf>.image-NN.pP.png|jpg`, к сообщению НЕ прикрепляются (модель их не «смотрит» — только адреса в списке: «картинка N из <pdf>, стр. P, W×H»). Работает и для моделей без зрения. Выключатель: `ARCKEP_PDF_EMBEDDED_IMAGES=0`; путь к программе — `PDFIMAGES_BIN`; пределы памяти те же (`popplerRunner.ts`). Пределы против «бомб» (PDF приходит от кого угодно): распаковка по одной странице и только тех, где есть нужные картинки; по `pdfimages -list` оценивается сырой размер всех картинок страницы (тяжелее 512 МБ — страница пропускается, на файл — 1 ГБ), один файл ≤128 МБ (`prlimit --fsize`), папка ≤512 МБ, весь разбор ≤300 с; картинка больше 36 Мпикс не берётся. Шрифты PDF не трогаем (у макетов из Figma это Type 3 глифы).
- **Фоновая подготовка PDF** (`pdfPrepare.ts`): на тяжёлом PDF (макет письма 603×5532 пт) страницы рисовались 11–19 с, и модель начинала отвечать только после них. Теперь подготовка (вшитые картинки, затем страницы) стартует при загрузке файла — `POST /files` (`packages/openapi/src/services/file.service.ts`, не для документов базы знаний), пока человек пишет сообщение. Результат лежит в записи файла: `files.metadata.pdfPrep` (jsonb `||`, остальные ключи целы): ключи файлов-страниц, вшитые картинки, число страниц; повторно файл не рисуется. `execAgent` ждёт готовности не дольше `ARCKEP_PDF_PREPARE_WAIT_MS` (45 000 мс; было 5000 — 19.10 первый ход по PDF ушёл без страниц, и модель сочинила другое письмо); не успело — модель получает текст, а на строке PDF в `<attachments>` стоит пометка «страницы ещё рисуются…», ошибки нет; вшитые картинки (они готовятся первыми) идут в список сразу. На следующем ходе страницы подхватываются из записи в историю (в память, без записи в базу: `enrichHistoryWithPdf`), пометка снимается. Одновременно — не больше `ARCKEP_PDF_PREPARE_PARALLEL` (2) задач. Версия записи подготовки — 2 (`PDF_PREP_VERSION`): записи версии 1 не используются и пересчитываются. Выключатели: `ARCKEP_PDF_PREPARE_ON_UPLOAD=0` (не готовить при загрузке; `execAgent` всё равно запустит и подождёт до 45 с), `ARCKEP_PDF_PAGE_IMAGES=0`, `ARCKEP_PDF_EMBEDDED_IMAGES=0`. Запись в `files.metadata` недоверенная (tRPC `file.createFile` принимает любой `metadata` от клиента): всё, что читается из базы, проходит `verify` в `pdfPrepare.ts` — строгий формат, каждый `fileId` обязан быть файлом этого человека (`FileModel.findByIds` с его `userId`), ключ страницы берётся из записи ЕГО файла, а не из записи подготовки; подделка считается отсутствием записи (файл готовится заново), лишние поля отбрасываются. Живые задачи и ожидание — в памяти процесса: движок один процесс (`node server.js`); при нескольких процессах запись `processing` другого процесса считалась бы мёртвой. Страницы рисуются и для моделей без зрения (при загрузке модель неизвестна) — им они не отдаются. Пределы poppler подняты (страница 180 с, весь файл 420 с): под `nice 10` на занятом хосте (load 10–14 на 4 ядра) рисование растягивалось в разы, и прежние 60 с давали «нарисовано ничего»; модель результат не ждёт.
- **Описание макета PDF** (`pdfLayout.ts`, `layoutRaster.ts`, `packages/prompts/src/prompts/files/layout.ts`, 19.10.2026): люди присылают макет письма или страницы в PDF и просят сверстать HTML «точно по макету»; на глаз модель путала картинки, меняла значки на текст и брала шрифт мельче. Ручная проба 19.10 с точным описанием макета подняла похожесть результата с 63,5 % до 89,3 %. Теперь описание снимает программа в фоне, шагом после страниц (запись `files.metadata.pdfPrep.layout`): строки текста (`pdftohtml -xml -zoom 1`: место, размер шрифта, жирность, ссылка; путь — `PDFTOHTML_BIN`; цвет текста — с нарисованной страницы), блоки (заливки, рамки-контуры, линии, скругления по смещению начала заливки во втором ряду точек), вырезки (видимая часть вшитых фото — картинку pdftohtml сравнивают с нарисованной страницей: рамка карточки обрезает фото; векторные значки и логотипы — «чернила» без текста, фото и рамок; файлы человека `<pdf>.crop-NN.pP.jpg|png` в 2×) и подсказка шрифта (отношение ширины строк к Arial — `layoutFontWidths.json`, `scripts/arckep/gen-layout-font-widths.py`). Страница второй раз не рисуется: берётся та же PNG, что режется на куски (`keepRasters` в `pdfPages.ts`, не больше 160 МБ). Описание идёт ВСЕМ моделям, в том числе без зрения (у них это единственный способ «увидеть» макет; в `layout_docstring` для них сказано «картинок страницы у тебя нет: верстай только по этому описанию»; картинки страниц по-прежнему только моделям со зрением). У каждой вырезки подпись, где она стоит: «в кнопке «Профиль»», «в карточке «Название услуги»», «в рамке …», «в блоке …» (самый внутренний блок, в который она попадает, и первая строка его текста) или «под/над/слева от/справа от «…»» (ближайшая строка в пределах 150 пт), текст — до 40 знаков. Блок `<layout file=…>` в `<files_info>` после `<attachments>` (до ~24 000 знаков; строки обрезаются с пометкой), в текущем сообщении и в истории; текст собирается при каждом ходе из записи (`message.metadata.layouts` — только в памяти хода, в базу не пишется). Подписи кусков страниц содержат диапазон `y` в точках страницы, а у вшитой картинки в списке вложений — её место на странице. Пределы: ≤10 страниц, ≤800 строк на страницу и ≤2000 всего, ≤40 вырезок на файл, ~120 с на всё; любая ошибка — описания нет, остальное как раньше. Описание делается только когда файл похож на макет (блоков и вырезок не меньше `LAYOUT_MIN_ELEMENTS` = 4): у обычного текстового PDF его нет. Выключатель: `ARCKEP_PDF_LAYOUT=0` (нужны страницы-картинки: без `ARCKEP_PDF_PAGE_IMAGES` описания нет). Всё из PDF (строки, ссылки, названия шрифтов, имя файла) — чужой текст: в блок оно попадает без угловых скобок и переводов строк. Правило для модели — в `ARCKEP_DEFAULT_SYSTEM_ROLE` и разделе HTML навыка Artifacts: верстать по числам описания, картинки и значки только из его вырезок, значок не заменять текстом и эмодзи, не писать «совпадает точно», а перечислить отличия; если человек дал свои адреса картинок (свой сайт, свой почтовый сервис) — ставить их вместо вырезок на нужные места, а когда неясно, какой адрес куда, спросить до вёрстки (последняя строка блока `<layout>` говорит то же).
- **Системный промпт** (`ARCKEP_DEFAULT_SYSTEM_ROLE`, +130 токенов): готовую HTML-страницу, письмо, лендинг, SVG отдавать в `<lobeArtifact>`, не блоком кода; картинки в HTML брать из `<attachments>` и результатов `create_image`/`get_image` (заглушка — только если подходящей нет); шрифты — Google Fonts по ссылке, другой шрифт скачать в песочнице, сохранить файлом чата и подключить через `@font-face` по ссылке `/chat/f/…`. Раздел HTML навыка Artifacts (`packages/builtin-skills/src/artifacts/content.ts`) согласован с этим: запрет «никаких внешних картинок» заменён разрешением адресов вложений и результатов, `/api/placeholder` остаётся запасным. Раздел React навыка не менялся (там внешних картинок по-прежнему нет).
- **В истории студии** эти файлы видны как вложения сообщения (имена с `.part-NN-of-MM.` и `.page-NN.`): экран может их сворачивать по такому имени. Порядок вложений в базе теперь стабильный (`createdAt`, имя).

## Решения

- Вопрос: чем рисовать страницы PDF — pdfjs-dist (уже в зависимостях) или poppler?
- Взяли: poppler отдельным процессом. Отвергли: pdfjs + @napi-rs/canvas в процессе движка.
- Почему: изоляция разбора чужих PDF (зависание и падение не трогают сервис, есть тайм-аут), нет холста и памяти высоких страниц в процессе движка, зрелый рендер шрифтов; движок работает на хосте, poppler там стоит. Нет poppler — остаётся текстовый слой.
- Вопрос: с какой высоты резать картинку на куски?
- Взяли: выше 3072 после сжатия по ширине (а не «около 2048»), куски по 2048.
- Почему: экран телефона 1290×2796 и страница A4 при ширине 1536 (2172) должны остаться одной картинкой, а резка нужна длинным макетам.

- Вопрос: где хранить список вложений для модели — в тексте сообщения человека или рядом?
- Взяли: `messages.metadata.attachments`, рендер в контексте модели. Отвергли: дописывать список в `content` сообщения.
- Почему: человек в студии не должен видеть служебный список; из метаданных он читается из базы на каждом шаге и в истории, текст остаётся как написал человек.
- Вопрос: рисовать страницы PDF прямо в `execAgent` или заранее?
- Взяли: заранее, в фоне при загрузке файла; `execAgent` ждёт ≤45 с (сначала было 5 с) и без страниц не падает. Отвергли: рисовать синхронно (11–19 с до начала ответа на тяжёлом PDF) и отдельную очередь/таблицу (хватило `files.metadata`).
- Почему: студия грузит файл раньше, чем человек отправит сообщение; движок — один долгоживущий процесс, фон безопасен. Цена: страницы рисуются и тем, кто потом выберет модель без зрения.
- Вопрос: ссылки `/chat/f/<id>/` в списке вложений — публичные, не рискованно ли?
- Взяли: как есть (так просил владелец: адрес вставляется в HTML-предпросмотр и письмо). Отвергли: подписанные ссылки с сроком.
- Почему: `/f/:id` — штатный прокси файлов LobeChat без входа (запись ищется без userId, ответ — 302 на подписанный адрес на 5 минут); id — 12 знаков из 62 (около 71 бита), генератор `nanoid/non-secure` (не криптостойкий): перебором не угадывается, но и не секрет; адрес в письме должен жить дольше любого срока. Риск: у кого есть ссылка, тот видит файл, а модель может вставить её в публичную страницу; секретные вложения человек обрабатывает на свой риск.
- Вопрос: вшитые картинки PDF прикреплять к сообщению или только давать адреса?
- Взяли: только адреса в списке (файлы человека без привязки к сообщению). Отвергли: прикреплять как картинки.
- Почему: модель вставляет их в HTML по адресу, а «смотреть» их ей незачем — страницы уже даны целиком; иначе +13 картинок в запрос и в историю студии.

- Вопрос: описание макета — просить модель описать картинку или снять с файла программой?
- Взяли: снимать программой (pdftohtml + пиксели нарисованной страницы). Отвергли: отдельный вызов модели «опиши макет» и зрение без чисел.
- Почему: модель по картинке даёт шрифт 14–15 вместо 20 и путает места; числа из файла дали 111 строк на своих местах и 19 из 20 картинок до пикселя. Стоит секунды процессора, а не платного вызова.
- Вопрос: описывать каждый PDF или только макеты?
- Взяли: только когда нашлось не меньше 4 блоков и вырезок (`LAYOUT_MIN_ELEMENTS`). Отвергли: описание у каждого файла.
- Почему: описание до 24 000 знаков повторяется в запросе на каждом ходе; у договора или статьи оно только съело бы деньги. Порог низкий, чтобы письма и лендинги проходили; поменять — константа.
- Вопрос: вырезки значков — с прозрачным фоном или как на странице?
- Взяли: как на странице (PNG с цветом фона блока, в котором значок стоит), в 2×. Отвергли: прозрачные вырезки.
- Почему: в PDF фон и значок не разделены; восстанавливать альфу по пикселям ненадёжно, а на том же фоне, что в макете, вырезка встаёт без швов. Значок на другом фоне модель увидит по картинке страницы.

## Свои MCP людей (этап 3, 19.10.2026; ТЗ — `docs/plans/chat-skills-tools-tz-2026-10-19.md` в репозитории студии)

- **Строка подключения** `umcp-` + 12 знаков `[a-z0-9]` (идентификатор выдаёт бэкенд студии; префикс `mcp-arckep-` у своих запрещён — каталог движка собирается по нему). `customParams = {mcp: {type: 'http', url}, arckepUserMcp: {kind, sealed, display}}`: `sealed` — шифротекст `enc:v1:…` настроек (расшифровывает только шлюз), `display` — что показать человеку. `sealed` наружу не отдаётся ни в одном ответе REST (`summarizeConnector` берёт только `kind` и строки `display`).
- **REST** (только служебный вход студии, `authType = arckep-service`): `POST /api/v1/plugins/user-mcp` `{identifier, kind, sealed, display, title, description}` — зовёт шлюз `USER_MCP_GATEWAY_URL` (`initialize` → `notifications/initialized` → `tools/list`, общий срок 120 с, `src/server/services/userMcp/gateway.ts`), собирает manifest, пишет строку; ошибка шлюза уходит с его текстом и статусом (402/429/… проходят, 401/403/5xx → 502, нет ответа → 504; 503 — только если шлюз сам подсказал его в `error.data.status`, например «Сервер запускается, повторите через минуту»), строка не пишется. `POST /api/v1/plugins/user-mcp/:id/refresh` — перечитать инструменты (шлюзу уходит `X-Arckep-User-Mcp-Refresh: 1`: он держит `tools/list` в кэше 10 минут; при создании заголовка нет). `GET /api/v1/plugins/catalog` отдаёт и СВОИ `umcp-*` этого человека (`installed: true`, с `userMcp`; чужих нет, общий каталог по ним не собирается; по этому ответу экран строит список и считает предел «10 своих»), `install` для `umcp-*` — 404. Удаление — обычный `DELETE /api/v1/plugins/:id`; `PATCH` настроек у `umcp-*` — 400. Список инструментов чужого сервера сжимается: имя `[\w-]{1,64}` без `____`, до 60 инструментов, описание до 1000 знаков, схема до 16 КБ (иначе пустая), ответ шлюза читается потоком до 4 МБ.
- **Вызов** (`withUserConnectionParams` → `userMcpConnectionParams`): адрес только `USER_MCP_GATEWAY_URL`, заголовки `X-Arckep-User` (номер выводит сервер), `X-Arckep-User-Mcp-Id`, `X-Arckep-User-Mcp-Config` (= `sealed` из строки ЭТОГО человека), `X-Arckep-Topic` (тема своя; без своей темы вызов отклоняется, как у E2B). `settings`, заголовки и `auth` из манифеста не читаются. Значения заголовков в журнал MCPService не пишутся (`sanitizeForLogging`).
- **Видимость для модели:** строка в `user_installed_plugins` + id в `plugins` помощника (включает сайт) → грузится по требованию (`isArckepLazyMcpConnectorId` знает префикс `umcp-`): в `<available_tools>` одна строка из `meta.title` и `meta.description`, схемы приходят по `activateTools`, дальше «подключённое помнится в теме». Выбранный на сообщение `umcp-*` включается сразу. В манифесте — `systemRole`: ответы чужого сервера — недоверенные данные.
- **Поиск подключений для модели:** встроенный `arckep-connectors` (`searchConnectors({query})`, пакет `builtin-tool-skills/src/arckepConnectors`, серверный рантайм `serverRuntimes/arckepConnectors.ts`) — только безголовый движок, не у ботов, по требованию. Каталог — `GET {IMAGE_STUDIO_API_URL}/api/internal/chat-mcp-catalog?q=&limit=5` с `x-arckep-token`, плюс установленные `mcp-*` / `umcp-*` человека; до 5 строк, на каждую `ARCKEP_CONNECT {"id","source","title"}`. Подключает человек кнопкой, ключи в чате не спрашиваются.
- **Метка темы и подтверждения** (`toolExecution/topicTrust.ts`): `topics.metadata.arckepUntrusted = {since, identifier}` ставится одним UPDATE (`jsonb_set`, без «прочитал-слил-записал») перед вызовом `umcp-*` и при подключении такого инструмента (шаг `activateTools` или включён на сообщение: чужие описания идут модели уже тогда). Отказ закрывающий: не удалось пометить — `activateTools` возвращает ошибку, `execAgent` не начинает ответ, вызов не уходит. Платные запуски студии (`isArckepPaidStudioTool`: у `mcp-arckep-studio-*` — `create_*`, `revise_*`, `replicate_*`, `chat_completion`, `decide`; у встроенной «Студии» — `createImage`, `createSpeech`) и вызовы, открывающие адрес (`isArckepPageOpeningTool`: `web_fetch` у `mcp-arckep-studio-web`, `crawlSinglePage` / `crawlMultiPages` у `lobe-web-browsing`, `saveSkillFromUrl` у `arckep-skills`; поиск не трогаем) в такой теме не выполняются (в карточке для страниц — «Открыть страницу <адрес>», без слова «платный»): запрос `{id, tool, identifier, argsHash, status, createdAt, decidedAt?}` пишется в `metadata.arckepConfirmations[id]` (id детерминирован от подключения, инструмента и sha256 канонического JSON аргументов), модель получает текст и строку `ARCKEP_CONFIRM {"id","tool","summary"}`. Переходы состояния — одним UPDATE со сравнением прежнего значения: выигрывает один. Одобрение и отказ живут 15 минут от решения, ожидающий запрос — 15 минут от создания, одобренное гасится на один вызов. `POST /api/v1/arckep/topics/:topicId/confirmations/:id` `{action}` (служебный вход, тема своя) → `{status}`; 404 — нет запроса или темы, 409 — решено иначе или уже выполнено, 410 — устарел. Тему выдаёт и история: вызов `umcp-*` или шаг `activateTools` с `umcp-*` в `pluginState.activatedTools` (страховка, если метку затёрла запись `metadata` целиком).
- **Защита MCP-клиента** (`toolExecution/mcpPolicy.ts`): stdio на сервере выключен; у `mcp-arckep-*` адрес только `ARCKEP_MCP_GATEWAY_URL_PREFIX` (по умолчанию `http://127.0.0.1:8410/mcp/`) или `ARCKEP_STUDIO_MCP_URL` (разбор адреса, не сравнение строк: `@`, `..`, `%2e%2e`, чужой порт и логин отклоняются); прочие сетевые подключения в безголовом режиме отклоняются; `X-Arckep-User` уходит только на эти адреса.
- **Переменные окружения:** `USER_MCP_GATEWAY_URL` (по умолчанию `http://127.0.0.1:8410/mcp/user-mcp`), `ARCKEP_MCP_GATEWAY_URL_PREFIX`; остальное — прежнее (`ARCKEP_STUDIO_MCP_URL`, `IMAGE_STUDIO_API_URL`, `ARCKEP_INTERNAL_TOKEN` / `LOBECHAT_BACKEND_KEY`, `ARCKEP_HEADLESS_TOOLS`).
- **Порядок выкладки:** до выкладки движка шесть подключений на `https://arckep.ru/mcp/mcp/<имя>` (amocrm, bitrix24, clickhouse, google-sheets, mysql, postgres) перевести на `http://127.0.0.1:8410/mcp/<имя>`: адрес вне списка отклоняется.

- Вопрос: запись разбора памяти (`memory-user-memory/providers/chatTopic.ts`) перезаписывала `metadata` целиком по снимку и стирала метку и запросы подтверждения.

- Вопрос: открывающие адрес вызовы — под подтверждение или нет?
- Взяли: да, `web_fetch`, чтение страниц и импорт навыка по ссылке; поиск нет (решение владельца 19.10). Почему: чужой сервер может попросить открыть адрес злоумышленника с данными беседы в запросе. Открытое: `execute_code` песочницы E2B тоже выходит в сеть — под подтверждение не ставили.

## Известный риск по своим MCP

- Код в песочнице E2B (`execute_code`, команды навыков `lobe-skills`) выходит в интернет и в теме с чужим инструментом (`umcp-*`) выполняется без подтверждения. Чужой сервер может по указанию в своём ответе заставить модель отправить данные беседы наружу. Решение владельца 19.10: не трогать — подтверждение на каждый запуск кода сделало бы работу с данными невыносимой. Открывающие адрес вызовы (`web_fetch`, чтение страниц, `saveSkillFromUrl`) под подтверждением. Варианты на будущее: подтверждение `execute_code` с отказом при коде длиннее лимита (код показывать целиком, как адреса) или режим «запрещено всё, кроме списка» для тем с меткой.

## Сверка письма с макетом и правки артефакта кусками (`arckep-layout`, 19.10.2026)

Модель верстает HTML по описанию макета PDF (`<layout>`, этап A). Проба 19.10: один круг «сверить и поправить» в переписке исправил названное, но сдвинул соседнее на +28 px, а каждый круг в обычном чате дороже предыдущего (круг 2 — 41 ₽ против 22 ₽: модель получает всю переписку и печатает письмо целиком). Теперь модель пишет письмо один раз и зовёт `checkLayout`; круги движок крутит сам, вне переписки.

- **Инструменты** (`packages/builtin-tool-arckep-layout`, серверное выполнение `serverRuntimes/arckepLayout.ts`, логика `src/server/services/arckepLayout/`): `checkLayout({identifier, file?})` — сверить последнюю версию HTML-артефакта с макетом (`file` — имя PDF, по умолчанию последний PDF темы с описанием; имя ищется точно, потом по вхождению без регистра); `editArtifact({identifier, edits:[{find,replace}]})` — правки последней версии по просьбе человека (≤30; `find` встречается ровно один раз, иначе правка не применяется и причина видна в ответе; пустая `replace` удаляет кусок). HTML модель не передаёт. Ответ обоих — короткий текст и готовый тег `<lobeArtifact identifier type="text/html" title src="https://arckep.ru/chat/f/<id>/"></lobeArtifact>` (экран студии умеет такие теги, PR студии #694); модели сказано показывать результат только этим тегом и HTML заново не печатать.
- **Когда инструмент в ходе** (`enable.ts`, `execAgent`): в теме есть PDF (вложен сейчас или раньше) или HTML-артефакт в прежнем ответе помощника; не боты, не выключенное человеком (`excludePluginIds`). Не «по требованию»: схема ≈ 0,5 тыс. токенов, модель должна вызвать его сама (`discoverable:false, hidden:true`, в `arckepLazyToolIds` его нет). Выключатель: `ARCKEP_LAYOUT_CHECK=0`.
- **Где взять последнюю версию:** сообщения ассистента темы и результаты самого `arckep-layout` (в них стоит готовый тег — версия учитывается, даже если модель не повторила тег в ответе); тело тега или файл по `src` (только файлы этого человека, ≤2 МБ). Текст текущего хода к моменту вызова инструмента уже в базе: `call_llm` пишет `content` до запуска инструментов. Модель и поставщик хода — из записи сообщения ассистента; номер этого сообщения инструменту отдаёт новое поле `ToolExecutionContext.parentMessageId` (его кладут `call_tool` и `call_tools_batch` в `RuntimeExecutors`).
- **Круг** (`check.ts`): отрисовка (бэкенд студии `POST /api/chat/layout-render`, PR студии #695, заголовок `X-Arckep-Token`) → сравнение с описанием → правщик (`editor.ts`) → правки «найти → заменить» → снова отрисовка и сравнение. Не больше 3 кругов (`ARCKEP_LAYOUT_CHECK_ROUNDS`), общий бюджет ~240 с (`ARCKEP_LAYOUT_CHECK_BUDGET_MS`; нового круга не начинаем, если осталось меньше самого долгого прошлого), стоп раньше при похожести ≥97 % и пустом списке расхождений. Лучшая версия сохраняется файлом чата человека `files/<userId>/<nanoid>/<identifier>-check-<n>.html` (`text/plain; charset=utf-8`, адрес как `fileAddress`).
- **Приём версии** (`judge`): похожесть по картинке выросла И нет новых расхождений в строках и картинках, которые были на месте, И прежние расхождения не выросли больше чем на 6 px. Иначе откат к лучшей версии и ещё круг с пометкой правщику, что прошлые правки сделали хуже и что именно. Нет картинки макета или снимка — «выросла» заменяется на «расхождений стало меньше».
- **Сравнение** (`compare.ts`, порт `compare.py` пробы 19.10; на данных пробы даёт те же числа: r1 — 13 сдвигов по x и app-phone, r2 — 55 строк и 11 картинок): строки по началу текста; высота — относительно самого частого сдвига (кандидат с наибольшим числом сдвигов в окне ±3 px, итог — среднее сдвигов окна; у `compare.py` брался край «полки» кандидатов, из-за чего допуск ±6 был несимметричным); у строк «по центру» левый край не сравнивается; размер шрифта — от 1 px; картинки — по адресу вырезки (адрес с хостом и без — одна картинка), чужие адреса человека — по месту и размеру (пересечение ≥30 %); допуск ±6 px; `scroll_width` > окна — «выходит за ширину»; не загрузившаяся картинка и `failed_images` — расхождения. Окно письма — колонка содержимого (x0–600 при странице 603), а не вся страница.
- **Приёмы, которые выбросит почта** (`techniques.ts`, живая проверка 19.10: Gemini 4 Argon по точным координатам `<layout>` расставил всё через `position:absolute` — 77 мест, 0 таблиц, похожесть 93,6 %, а в Gmail и Outlook такое письмо разваливается): расхождения первого ряда, они важнее похожести. Считаются `position:absolute|fixed`, `display:flex|grid|inline-flex|inline-grid` (и старые приставки `-webkit-box`, `-ms-flexbox`), `float:left|right`, внешние таблицы стилей (`<link rel=stylesheet>`, `@import`) и любые `<script>`. Проверка идёт всегда, когда артефакт сверяется с макетом PDF, и только по тексту HTML (значения `style="…"` и блоки `<style>`; комментарии, код скриптов и упоминания в тексте письма не читаются), поэтому работает и когда отрисовка недоступна. **Шрифты Google (`fonts.googleapis.com`, `fonts.gstatic.com`) не считаются:** правила разрешают их ссылкой, а без шрифта письмо меняет только начертание. Правило приёма версии (`judge`): приёмов не было, а в новой версии появились — не принимается, как бы ни выросла похожесть; приёмы были — новая принимается, только если их строго меньше, нет новых видов и осталось ≥80 % строк макета (похожесть при уборке может падать); убраны совсем — принимается при тех же 80 % строк. Правщику — отдельный раздел «Приёмы, которые выбросит почта» (число, виды, примеры кода) и абзац в системном тексте: заменять расстановку таблицей. Модели в ответе `checkLayout`: если приёмы остались, письмо надо переписать обычным потоком (вложенные таблицы, стили в style) новым `<lobeArtifact>` с тем же identifier и вызвать `checkLayout` ещё раз; обычный «покажи только этим тегом» в этом случае не выдаётся, тег идёт запасным. Выключатель: `ARCKEP_LAYOUT_TECHNIQUES=0` (тогда версия принимается только по похожести).
- **Картинки** (`pictures.ts`, `mockup.ts`): макет — склейка кусков страницы (`record.pages` с диапазоном y) к «1 пт = 1 px»; похожесть — полосы по 400 пт, доля точек с разницей яркости ≤40 (строки, которых нет с одной стороны, — разные), итог — среднее по полосам. Правщику (только модели со зрением) уходят в одном сообщении как `data:`-адреса: обзор «макет | письмо» во всю длину и до 3 крупных пар по полосам; красная рамка — строка/картинка не на месте, жёлтая — разница по картинке без замеренной причины.
- **Правщик** (`editor.ts`): системный текст + одно сообщение (HTML, расхождения сгруппированы по блокам макета, ≤30 пунктов; одинаковый сдвиг у ≥4 строк подряд сворачивается в один пункт «причина выше»; картинки); без переписки. Ответ: «что вижу» (в т. ч. то, чего линейка не меряет: цвет, жирность, лишние линии, обрезка), потом JSON-массив правок; битый — круг пропускается. Тот же поставщик и модель, что в ходе; ступень рассуждений — `low` (или ближайшая) по тем же таблицам, что у `/responses` (`reasoningLevels.ts`).
- **Деньги и пределы:** вызовы правщика идут через `initModelRuntimeFromDB(…, {topicId, assistantMessageId})` — шлюз бэкенда списывает с человека как обычный ход и пишет `chat_token_charges` в эту тему. Отрисовка бесплатна, у бэкенда 60 в час и 2 одновременных на человека. Ошибка первой отрисовки (429/502/413/422/сеть) — модели честный текст «сверка сейчас недоступна» без падения хода (файл не сохраняется, повторно не звать); позже в цикле — остановка с причиной, лучшая версия всё равно показывается. Ни одна ошибка не глотается: `console.warn` с темой и человеком, `debug lobe-server:arckep-layout*`.
- **Ловушки:** (1) `sharp.extract` до `composite` режет основу, а не результат — склейку шириной 600 при странице 603 надо обрезать отдельным шагом; (2) JPEG 4:2:0 размывает тонкие цветные рамки до розового — пары для правщика кодируются 4:4:4; (3) модель может не повторить тег в ответе — поэтому версия берётся и из результата инструмента; (4) в тестах `packages/const` из своей папки не запускаются (setup ищет `@/locales`) — правила модели проверяет `htmlDeliveryRules.test.ts`; (5) на базовой ветке `claude/engine-pdf-layout` уже падают 31 тест в `serverRuntimes/__tests__/message.test.ts`, `topicReference.test.ts` и `toolExecution/__tests__/deviceProxy.test.ts` — к этой работе отношения не имеют; (6) фикстуры сравнения (`arckepLayout/__tests__/fixtures`) — строки обрезаны до 24 знаков, настоящие PDF и снимки в репозиторий не кладём; `live-absolute.html` — живое письмо с 77 `position:absolute`, текст в нём тоже обрезан до 24 знаков, разметка прежняя.

## Решения по сверке

- Вопрос: кто крутит круги «сверить и поправить» — модель в переписке или движок?
- Взяли: движок, вне переписки; правщик получает только текущий HTML, список расхождений и картинки, отвечает правками, а не письмом целиком. Отвергли: ещё один круг в чате и «пусть модель сама сравнит по картинке».
- Почему: круг в переписке дорожает (вся история + письмо целиком) и ломает соседнее; числа расхождений и откат по ним дают то, чего на глаз не сделать.
- Вопрос: когда принимать версию?
- Взяли: только если похожесть выросла и нигде не стало хуже. Отвергли: «похожесть выросла» одна и «расхождений стало меньше» одно.
- Почему: проба 19.10 — +28 px ниже одной строки при исправленных сдвигах по x; одна из двух метрик это пропускает.
- Вопрос: что важнее — похожесть по картинке или то, переживёт ли письмо почту?
- Взяли: почта. Приём вёрстки, который выбросит почта, — расхождение первого ряда; версия с такими приёмами не принимается, даже если похожесть выше; уборка идёт шагами, похожесть при ней может падать. Отвергли: считать приёмы одним из расхождений наравне с положением строк.
- Почему: 19.10 письмо из 77 `position:absolute` дало 93,6 % на экране и развалилось в Gmail/Outlook; похожесть этого не видит. Платный правщик с лимитом 30 правок за круг уберёт 77 мест не всегда — тогда модель получает прямую просьбу переписать письмо таблицами и вызвать `checkLayout` ещё раз.
- Вопрос: ссылки на шрифты Google — приём или нет?
- Взяли: не приём. Отвергли: считать любой `<link rel=stylesheet>`.
- Почему: правила модели прямо разрешают Google Fonts ссылкой; иначе модель, следуя правилу, получала бы вечное расхождение. Без шрифта письмо только меняет начертание, раскладка не рушится.
- Вопрос: инструмент по требованию или сразу?
- Взяли: сразу, но только когда в теме есть PDF или HTML-артефакт. Отвергли: ленивая подгрузка через activateTools.
- Почему: модель должна вызвать `checkLayout` сама после вёрстки, лишний шаг подключения ей мешает; схема мала, а в темах без макета и артефактов её нет.
